Narrative 继续使用六字段 JSON：`mode`、`why_this_mode`、`working_title`、`reader_promise`、`core_judgment`、`story_path`。现有审批、解析和 Writer 路由沿用原结构。Writer 自行决定段落、详略与行文，Narrative 交付可展开的内容方向。

## 试验结论与未采用项

| 试验 | 全文阅读后的决定 |
| --- | --- |
| News/Deep Writer 与 Light 联动重写 | 同题 Deep 的联动结果没有优于旧稿；News 尚未验证。这组 system 不进入本次部署。 |
| 固定输入比较 Sol、Luna、DeepSeek Flash、DeepSeek Pro | Pro 的这一篇最集中，Flash 也更有作者口吻；两者都把 nginx 三次修复中两次改变镜像、端口的转折概括掉了。Pro 保留为后续候选，不直接替换线上模型。 |
| 自写独立文风编辑 | 几乎没有改变全文，不增加正式节点。 |
| 完整原版 Humanizer | 有局部精简，整篇组织仍偏验证和核查，不作为已解决文风问题的方案。 |
| Humanizer 加全量 JSON | 没有整体变好，还把一处“可能”改成确定判断；不采用整包注入。 |
| Humanizer 加十分之一 JSON | 合并重复开头，省掉一段概念铺垫，保住“可能”；略顺，但仍按参数、验证、加工与成本展开。保留压缩参考库，不以此认定文风问题已解决。 |

各轮复用已保存基线，新增输出均读完全文，没有手工改大纲或改文章冒充模型验证。上述结论来自同一个 911 题目，不代表其他选题或英文的稳定效果。
