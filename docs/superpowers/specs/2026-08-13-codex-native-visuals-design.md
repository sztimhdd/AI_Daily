# Codex Native Visuals 子系统设计

**状态：** 已批准 | **日期：** 2026-08-13 | **字数：** ~900 字

## 1. 架构决策

### 执行平台

Codex Desktop / 对话界面是日常执行平台，负责选题、写稿、视觉规划、图像生成、验收。Python CLI 负责确定性状态管理、文件校验、规范命名、合并组装、发布。二者分工明确：Codex 做编辑决策，CLI 做机械执行。

### 运行状态存储

- **运行时状态：** `.local/runs/<date>/` 存放视觉计划、候选图像、原始响应、日志、缓存。不进入 Git。
- **最终产物：** GitHub 仅存放已发布的最终文章及被接受的图像。路径格式：`outputs/YYYY/MM/DD/<article-slug>/`。

## 2. 无图可发布原则

稿件本身必须完整自洽，插图是增强而非必需。视觉计划的四种终态：

| 状态 | 含义 |
|---|---|
| `complete` | 所有计划图像均已生成并采纳 |
| `partial` | 部分图像成功，部分缺失 |
| `unavailable` | 图像生成完全不可用 |
| `skipped` | 未启动视觉计划 |

任何情况下，组装阶段必须拒绝：未解析的占位符、空 `![]()` 语法、指向不存在文件的链接、无图配文、以及依赖图像存在的文字表述（如"如下图所示"）。

## 3. 视觉计划

视觉计划与稿件草稿分离。稿件撰写时不插入任何占位符，写完后由 Codex 独立生成一个 JSON 视觉计划。

计划内容：1 张可选封面 + 0–3 张正文图像。每张图像记录：插入锚点（段落序号或标题引用）、类型（Analyst/Architect/Insider/Memer，源自原 n8n 工作流定义的四种类型）、英文提示词、中文图注、状态（pending/generated/failed/skipped）。

## 4. 生成与验收流程

Codex 负责编辑策划和图像生成，Python CLI 负责后续处理：

1. **视觉计划：** Codex 阅读稿件，决定图像位置和类型，写入视觉计划 JSON。
2. **图像生成：** Codex 调用 `image_gen` 工具，按提示词生成图像，保存到 `.local/runs/<date>/visuals/<id>.source.<ext>`。
3. **校验与采纳：** Python CLI 验证图像格式、尺寸、完整性，按规范命名并移入生产路径。
4. **合并：** Python CLI 读取视觉计划，将成功图像插入稿件锚点，移除未生成图像的锚点记号，输出最终文章包。
5. **发布：** 不含任何未解析占位符。

## 5. 幂等与重试

每项视觉计划条目携带 `prompt_sha256` 和 `image_sha256`。重跑时：
- `status: generated` 且 `image_sha256` 匹配已有文件 → 跳过。
- `status: generated` 但文件缺失或损坏 → 重新生成。
- `status: failed` 且 `prompt_sha256` 不变 → 可重试（由 Codex 判断）。
- 提示词变更 → `prompt_sha256` 变化 → 旧结果失效，必须重新生成。

## 6. 测试与验收标准

### 单元测试覆盖
- 视觉计划的创建、校验、锚点查找。
- 图像校验（格式、尺寸、完整性）。
- 组装阶段的图像插入、占位符清除、状态写入。
- 幂等跳过逻辑。

### UAT 场景
- 2 张正文图像全部成功 → `visuals.complete`，最终文章含两张图。
- 无图像计划 → `visuals.skipped`，无 `images/` 目录。
- 1 张成功 1 张失败 → `visuals.partial`，仅含成功图像，无占位符残留。
- 全部失败 → `visuals.unavailable`，纯文本发布。
- 中断恢复 → 已生成的图像不被重新生成。
- 提示词变更 → 旧图像失效，重新生成。

## 7. 明确排除范围

- API 供应商适配层（OpenAI / Gemini 等 API）。图像生成仅依赖 Codex 内置 `image_gen` 工具，V3 可能引入适配器。
- 无人值守服务端或守护进程模式。AI Daily 在 Codex Desktop 会话和 Automation 心跳中运行。
- 图像后处理（裁剪、缩放、增强）。仅做格式与尺寸校验。
- ChatGPT Image 导出作为主图像来源。旧 `cover.py` 已弃用。
